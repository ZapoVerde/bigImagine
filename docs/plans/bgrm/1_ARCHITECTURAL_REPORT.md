# Architectural Report — Character Image Background Removal

## 1. High-Level Goal & Rationale

BigImagine must support optional background removal as a **post-processing stage applied after successful character image generation**, rather than as a property of any particular image generator.

The feature applies only to **character imagery**:

- Portrait Studio renders;
- RP character portrait/autofire renders.

It does **not** apply to BigImagine's location/chat-background subsystem.

Background removal is initially performed by **Runware** through a dedicated **BGRM engine profile**. BigImagine's current image “connections” are configured engine profiles rather than minimal provider credential objects, so BGRM should follow that same model instead of introducing a second connection abstraction.

The source character image may have been generated by any compatible image provider.

The architecture must support at least:

- **Pollinations generation → Runware background removal**;
- **Runware generation → Runware background removal**.

When the source image comes from Pollinations, BigImagine passes the public image URL to Runware.

When the source image was generated by Runware, BigImagine may pass Runware's image UUID directly when available.

In neither case should BigImagine download, locally persist, proxy, or re-upload the intermediate image bytes.

Background removal remains optional. Character image generation must continue to work normally when BGRM is disabled or unavailable.

---

## 1.1 Detailed Description

The desired character-image pipeline is:

```text
generation
    ↓
generated image reference
    ↓
optional background removal
    ↓
final image URL
    ↓
persistence / cache / UI
```

The generated image reference contains enough information to identify the already-generated image without requiring BigImagine to possess the image bytes.

### External/public URL source

A provider such as Pollinations produces a publicly reachable image URL.

```text
Pollinations
    ↓
public generated-image URL
    ↓
Runware BGRM
    ↓
transparent Runware image URL
```

### Runware-native source

Runware generation produces an image already known to Runware.

```text
Runware generation
    ↓
Runware image UUID
    ↓
Runware BGRM
    ↓
transparent Runware image URL
```

Both paths produce the same application-level outcome: a final character image URL representing the asset the application should subsequently use.

The background-removal stage therefore consumes an **image reference**, not specifically a URL.

### BGRM engine profile

BigImagine's current image connection model represents configured **engine profiles** rather than provider credentials alone.

BGRM therefore uses its own dedicated engine profile:

```text
Runware BGRM profile
- purpose = bgrm
- provider = Runware
- RMBG model
- API credential
- relevant engine configuration
```

Generic image-profile fields that do not apply to background removal may remain unused by the BGRM capability. Their presence reflects reuse of the existing engine-profile persistence shape; it does not make BGRM a generator.

The BGRM engine profile defines **how background removal is performed**.

Individual character-image surfaces separately decide **whether background removal should be performed**.

The initial integrations are:

- **Portrait Studio** — optional BGRM for Generate, Preview and Retry;
- **RP character visual autofire** — optional BGRM for generated character visual combinations.

A character-image pipeline with BGRM disabled behaves exactly as it did before this feature.

A character-image pipeline with BGRM enabled performs generation first and only attempts BGRM after generation succeeds.

The image-generator responsibility ends when it has produced its normal successful result.

The BGRM responsibility begins with an existing image reference and ends with a final image URL.

# 2. Core Principles & Constraints

## 2.1 Governing Project Principles

### The relational store remains the canonical record

Rendered character images are derived working state. BGRM must not create a second media repository or introduce locally stored image assets as a new source of truth.

### IO and orchestration remain separate

External provider calls belong at an IO boundary.

The decision to perform generation, optionally perform BGRM, resolve the active BGRM engine profile, and choose the resulting usable URL belongs to orchestration.

Background removal must not become hidden behaviour inside an image generator.

### Runtime configuration is database-backed

The active BGRM engine profile and BGRM enablement settings must be runtime-editable and persisted in the database.

### Existing engine-profile architecture remains authoritative

Image connections currently represent configured engine profiles.

BGRM fits that model rather than introducing a second connection abstraction.

### Secrets remain write-only

Credentials used by the BGRM profile receive the same treatment as other provider credentials: encrypted at rest and never returned in plaintext through administrative surfaces.

### Provider-specific behaviour remains bounded

The application may exploit a provider-native image reference such as a Runware UUID when available, but application behaviour must not depend on every generator supporting one.

### Failure paths remain observable

A failed or skipped BGRM operation must be visible in diagnostics/logging rather than silently disappearing.

### Mobile usability remains required

Any BGRM controls exposed through existing user-facing panels or Settings must remain practical at phone width.

---

## 2.2 Change-Specific Principles

### BGRM is a post-process, not a generator

Background removal accepts an already-generated image and transforms it.

It must not become another prompt-driven image generator.

### BGRM uses a dedicated engine profile

The BGRM capability uses its own active Runware engine profile.

It does not borrow the portrait-generation profile merely because that profile may also use Runware.

### Generation and BGRM configuration are independent

A Pollinations generator may feed a Runware BGRM profile.

A Runware generator may feed the same Runware BGRM profile.

Changing the character image generator must not require changing the BGRM architecture.

### Runware is implementation one, not the application-level capability

Runware is the first supported BGRM backend because it provides a known, inexpensive, suitable API.

The application-level BGRM orchestration must remain conceptually replaceable so another backend can be added later without changing character-generation semantics or user-facing character-image surfaces.

### Intermediate image bytes do not pass through BigImagine

BigImagine may pass:

- an external public URL; or
- a provider-native image identifier.

It must not need to:

- download the generated image;
- write it to local storage;
- convert it to Base64;
- proxy it;
- upload it again to Runware.

### Prefer the strongest existing reference

When the source generator provides a provider-native reference directly usable by BGRM, that reference should be preferred.

When it does not, a supported public URL is sufficient.

The absence of a provider-native identifier is not an error.

### The final URL is the downstream image

When BGRM succeeds, its returned image URL becomes the image used by downstream character-image persistence, mapping, caching, and display.

The pre-BGRM generation URL is intermediate working state for that operation.

### A BGRM failure does not destroy a successful generation

Generation success has already produced a usable asset.

If background removal subsequently fails, the original generated image remains the fallback result.

BGRM is therefore **fail-open with respect to a successful generation**.

### BGRM must be explicitly enabled

Having an active BGRM engine profile does not mean every character image is automatically background-stripped.

Portrait Studio and RP character autofire opt into the post-process independently.

### Character-image surfaces use the shared BGRM capability

Portrait Studio and RP character autofire decide whether BGRM is enabled.

They do not duplicate Runware BGRM request logic or independently own BGRM provider implementation details.

### Cached character results must correspond to the selected processing mode

The application must not return a non-BGRM character asset where the effective request requires BGRM merely because the underlying character/outfit/expression matched a previous result.

Likewise, disabling BGRM must not accidentally force use of a previously stripped asset where the surface expects the raw image.

Where BGRM materially changes the resulting character asset identity, that state must be represented in the relevant character-image mapping/cache identity.

---

## 2.3 Explicit Non-Goals

The following are outside this architectural change:

- applying BGRM to location/chat backgrounds;
- modifying `generateLocationImage` or location-image combination caching;
- implementing BGRM providers other than Runware in the initial release;
- redesigning the overall image connection/profile architecture;
- separating provider credentials from engine profiles;
- migrating existing background or portrait engine-profile selection mechanisms;
- downloading or storing intermediate image files in BigImagine;
- introducing an application-managed image blob store;
- combining image generation and background removal into one provider-specific generator;
- requiring every generator to expose a Runware-style image UUID;
- performing BGRM before generation has completed successfully;
- changing the visual generation prompt because BGRM is enabled;
- changing character identity, outfit, expression, style, format, or other generation semantics;
- defining the VN-panel or cast-rail presentation of generated character images;
- adding automatic semantic judgments about which images need background removal;
- making BGRM failure equivalent to generation failure.

A future broader refactor may separate provider credentials from engine profiles, but that is explicitly outside this change.

# 3. Architectural Flows

## 3.1 User Flow

### BGRM engine-profile configuration

1. The operator creates or maintains a dedicated Runware BGRM engine profile.
2. The profile contains the Runware BGRM model, credential, and relevant engine configuration.
3. One BGRM profile may be selected as active independently of portrait-generation and location-background-generation profiles.
4. Activating a BGRM profile does not itself enable background removal on any character-image surface.

### Portrait Studio

1. The user chooses whether Portrait Studio should apply background removal.
2. Generate, Preview, or Retry performs normal portrait generation through the active portrait-generation profile.
3. If BGRM is disabled, the generated image is used normally.
4. If BGRM is enabled, the successful generated image is passed to the shared BGRM capability.
5. The capability resolves the active BGRM engine profile.
6. On BGRM success, the transparent image becomes the usable image.
7. On BGRM failure, the original generated image remains usable.

### RP character visual autofire

1. The user chooses whether RP character portraits should apply background removal.
2. Character visual autofire performs its normal Subject/Outfit/Expression/Style/Format render.
3. If BGRM is disabled, the normal generated result is used.
4. If BGRM is enabled, the generated result is passed to the shared BGRM capability.
5. The capability resolves the active BGRM engine profile.
6. The successful BGRM result becomes the image associated with that character visual combination.
7. If BGRM cannot complete, the generated image remains available rather than losing the render entirely.

## 3.2 Data Flow

### Pollinations source

```text
character generation request
      ↓
Pollinations
      ↓
public source-image URL
      ↓
BigImagine character-image orchestration
      ↓
BGRM enabled?
      ↓ yes
active BGRM engine profile
      ↓
source-image URL + BGRM profile configuration
      ↓
Runware BGRM
      ↓
transparent final URL
      ↓
character-image persistence / cache / UI
```

### Runware source

```text
character generation request
      ↓
Runware generation
      ↓
image URL + provider-native image identifier
      ↓
BigImagine character-image orchestration
      ↓
BGRM enabled?
      ↓ yes
active BGRM engine profile
      ↓
best compatible source reference
      ↓
Runware BGRM
      ↓
transparent final URL
      ↓
character-image persistence / cache / UI
```

The normal generated URL remains available as the fallback image until post-processing succeeds.

### Persistence boundary

Where an existing character-image pipeline persists or maps an image URL, it persists/maps the **effective final image URL**:

- generated URL when BGRM is disabled;
- BGRM URL when BGRM succeeds;
- generated URL when BGRM was requested but fails.

Intermediate image bytes are never persisted by this feature.

## 3.3 Logic Flow

```text
start character image request
      ↓
perform normal generation
      ↓
generation successful?
  ├─ no  → existing generation failure behaviour
  │
  └─ yes
       ↓
is BGRM enabled for this character-image surface?
  ├─ no  → use generated image URL
  │
  └─ yes
       ↓
is a usable active BGRM profile available?
  ├─ no  → record fallback reason
  │        use generated image URL
  │
  └─ yes
       ↓
select best compatible source reference
  │
  ├─ provider-native supported reference available
  │       → use provider-native reference
  │
  └─ otherwise
          → use public generated-image URL
       ↓
perform BGRM
       ↓
BGRM successful?
  ├─ yes → use returned BGRM image URL
  │
  └─ no  → record failure
           use generated image URL
       ↓
continue normal downstream character-image handling
```

No branch reruns generation solely because BGRM failed.

No branch downloads the image locally in order to continue.

---

## 3.4 Failure Flow

### Generation failure

Existing generation-failure behaviour remains authoritative.

BGRM is not attempted because there is no successful source image to process.

### No active BGRM profile

If a character-image surface requests BGRM but no usable active BGRM profile is available:

- the successful generation is not discarded;
- the original generated URL remains the usable result;
- the fallback is observable;
- downstream character-image handling continues.

### BGRM provider request failure

If Runware rejects the request, times out, returns a malformed response, or otherwise fails:

- the original generated image remains the usable result;
- generation is not repeated;
- the failed BGRM result is not persisted as though it succeeded;
- the failure is logged at the external-IO/orchestration seam.

### Source URL cannot be fetched by Runware

For external-provider images, Runware must be able to retrieve the supplied public image URL.

If it cannot:

- the operation follows the normal BGRM failure path;
- BigImagine does not fall back to downloading and uploading the image itself;
- the original generated URL remains available.

### Provider-native identifier unavailable

The absence of a provider-native image identifier is not itself a failure.

The pipeline uses the generated public URL instead.

### Active BGRM profile changes

Changing the active BGRM profile affects subsequent BGRM operations.

Already persisted character-image assets remain associated with the processing state under which they were created unless explicitly regenerated.

A profile change does not trigger a bulk recook.

# 4. Overall Acceptance Criteria

- **AC-01:** BigImagine can apply background removal to a successfully generated character image without background removal being implemented as part of the image generator itself.
- **AC-02:** A publicly reachable character image produced by Pollinations can be submitted to Runware background removal by reference, without BigImagine downloading or re-uploading the image bytes.
- **AC-03:** A character image produced by Runware can use a Runware-native image identifier for background removal when such an identifier is available.
- **AC-04:** The absence of a provider-native image identifier does not prevent BGRM when a supported public image URL is available.
- **AC-05:** Pollinations generation and Runware generation converge on the same application-level BGRM post-processing behaviour and final-image contract.
- **AC-06:** When BGRM succeeds, the returned transparent image URL becomes the effective image URL used by the downstream character-image pipeline.
- **AC-07:** When BGRM is disabled, character image generation and downstream handling behave as they did without the feature.
- **AC-08:** When generation succeeds but BGRM fails, the original generated image remains usable and the generation is not converted into a failed render.
- **AC-09:** A BGRM failure never causes the application to regenerate the source image solely to recover from background-removal failure.
- **AC-10:** BigImagine does not require local file storage, an image blob store, Base64 conversion, or image proxying to perform BGRM.
- **AC-11:** BGRM uses its own dedicated active engine profile independently of portrait-generation and location-background-generation profiles.
- **AC-12:** Activating or changing the BGRM engine profile does not replace or deactivate the independently selected portrait-generation or location-background-generation profiles.
- **AC-13:** Only character-image surfaces for which BGRM is effectively enabled attempt background removal; an active BGRM profile alone does not globally alter character images.
- **AC-14:** Portrait Studio can independently enable or disable BGRM for Generate, Preview, and Retry while using the shared active BGRM capability.
- **AC-15:** RP character visual autofire can independently enable or disable BGRM while using the shared active BGRM capability.
- **AC-16:** When the RP character-image pipeline reuses cached/mapped assets, it does not silently substitute an asset produced under an incompatible BGRM state.
- **AC-17:** When BGRM is requested but cannot be performed because no usable BGRM profile is active or external IO fails, the fallback to the original generated image is observable in diagnostics.
- **AC-18:** Provider secrets used by BGRM remain write-only and encrypted at rest while non-secret BGRM engine configuration remains visible and runtime-editable.
- **AC-19:** The architecture permits a future BGRM backend to be introduced without requiring character-image generators or user-facing character-image surfaces to duplicate or own provider-specific background-removal logic.
- **AC-20:** Existing image-engine profile architecture remains intact; this feature does not require separating provider credentials from engine profiles.
- **AC-21:** BigImagine's location/chat-background generation, caching, TOD logic, and display behaviour remain unchanged by this feature.
