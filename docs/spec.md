# SYSTEM SPECIFICATION v2: AGENTIC SECOND BRAIN PLATFORM
## ARCHITECTURE: MANIFEST-DRIVEN TOOL REGISTRY WITH RELATIONAL DATASTORE AND REPLACEABLE SURFACES

*Governed by `principles.md`. Where this spec and the principles disagree, the principles win — update this spec.*

---

### 1. SYSTEM OVERVIEW

This specification defines the architectural design for a self-hosted, multi-user, family-oriented "Second Brain" platform. The platform provides a **conversational-first** interface backed by an intelligent reasoning engine, with **optional specialist surfaces** (e.g. Notion) for structured domains like shopping lists, calendars, and recipes. It blends unstructured note-taking (semantic hybrid search) with deterministic household operations (grocery logistics, scheduling, email parsing) via a decoupled, data-first relational model.

The central design commitment: **all reasoning happens server-side, behind a stable API. Every client — chat UI, mobile app, Notion, or anything that replaces them later — is a replaceable consumer of that API, never a participant in it.**

---

### 2. CORE ARCHITECTURAL PRINCIPLES

*(Full detail in `principles.md`; summarized here as they bear on this spec.)*

- **Data-First Priority:** The relational store is the canonical record. Any external mirror (Notion, a cache, a rendered view) is reconstructible from it — never the reverse.
- **Reasoning Stays Server-Side:** The LLM is the only component that classifies, infers, or judges. Clients and integrations move and display data; they do not reason about it.
- **Reasoning Layer is Replaceable:** No prompt, tool manifest, or orchestration logic depends on one LLM vendor's specific behavior. Swapping models is a config change.
- **Interface Layer is Replaceable:** Every surface talks to the platform through a stable API. If Notion (or any client) becomes limiting, it is swapped behind that API — the platform is never bent to accommodate a surface's limitations.
- **Explicit Signal Outranks Inferred Signal:** User-provided hints (category ticks, tags) always outweigh automatic classification.
- **Server-Side Trust Scoping:** Which user's data an action touches is determined by trusted server context, never by the content of a message, note, or inbound webhook.
- **Chat is the Default:** Every interaction can be answered in conversation. Structured/specialist views are always additive, never required to see a result.

                                                                        **Correction 1 — Tag split.** `unstructured_notes.tags` is split into `auto_tags` (LLM-proposed at ingestion, noisy, many) and `pinned_tags` (small, user-curated, stable — the vocabulary used for manual tag-browse fallback when semantic search misses).

                                                                        **Correction 2 — Row-Level Security.** Every table carrying `user_id` gets a Postgres RLS policy scoping reads/writes to the requesting user. This is enforced in the database, not just the app layer — the app-layer/Cloudflare Access check is a second line of defense, not the only one.

**Correction 3 — `unstructured_notes` was missing two columns the ingestion pipeline (§6.1) actually produces.** `category` and `summary_short` are added alongside the existing `auto_tags`, mirroring `documents.summary_short`. `vector_embed` on both `unstructured_notes` and `documents` is `vector(2048)`, not `vector(1536)` as originally specified — Voyage AI's models don't support a 1536-dimensional output at all (confirmed against current docs: `voyage-4`'s `output_dimension` is one of {2048, 1024, 512, 256}); 2048 was chosen over the usual web-scale default of 1024 since storage/latency don't matter at household-notes scale and quality does. See `db/migrations/0003_phase3_schema_updates.sql`.

**Correction 4 — At-rest field encryption, and the scope it deliberately does not cover.** `unstructured_notes.raw_text` and `.summary_short` are encrypted (AES-256-GCM, `orchestrator/src/io/fieldCipher.ts`) before they're written, using a single server-held key (`BIGBRAIN_FIELD_ENCRYPTION_KEY`). `category`/`auto_tags` stay plaintext (needed for filtering, lower sensitivity); `vector_embed` cannot be encrypted at all without breaking pgvector similarity search, so it remains a queryable semantic fingerprint of the plaintext even though the plaintext itself isn't stored.

This protects against filesystem/DB access without the key — a stolen disk, a leaked backup, casual `psql` access — which is the threat model this was built for now (single user, host is otherwise trusted). It explicitly does **not** protect one user's content from another user who controls the deployment (e.g. a parent from a child's notes, in a future multi-user household) — whoever holds `BIGBRAIN_FIELD_ENCRYPTION_KEY` can always decrypt everything, and today that's the same person managing `.env`. A genuinely admin-blind scheme needs per-user key material the deployer never possesses (e.g. derived from a user-held secret, unlocked only for the duration of that user's own request) — deliberately deferred rather than built now: it would mean bigBrain can't process a user's content (ingest, embed, chat) unless that user's key is present for that specific request, which rules out any background/passive processing while they're not actively "unlocked," and it would need every user to supply real key material bigBrain's admin doesn't already hold — in tension with the stated goal of not asking users to maintain a credential beyond the household's existing Google/Cloudflare Access login. Revisit if/when the household actually grows past one person.

**Addition — `lists` / `list_items` (Phase 8 prerequisite).** A generic, domain-agnostic todo-list primitive, added while designing the Notion Sync Gateway: "Grocery List," "Home Depot Run," "Books to Read" are all just a `lists` row (`name`, optional informational `tags`) with `list_items` under it (`item_name`, `status` — `'pending'`/`'done'`, `completed_at`), not separate tables or a shopping-specific schema. `list_items.user_id` is denormalized (not just reachable via a join to `lists`) so RLS applies directly. Both tables carry the same `user_scoped` RLS policy as everything else. See `db/migrations/0004_lists.sql`.

Deliberately **not** wired into `shopping_logs` or any inventory/pantry concept: completing a list item only records that it happened (`status`/`completed_at`) — it does not insert into `shopping_logs`, even for a list tagged `shopping`. Considered and rejected: maintaining real inventory/pantry state was judged a large, open-ended effort (deduplication, staleness, "did I actually use it") for a payoff that doesn't exist yet. `shopping_logs`/§6.2's analytics engine stays fed only by the explicit `log_purchase` tool, entirely independent of lists. Revisit if a concrete downstream use for the linkage shows up (e.g. a time/deadline-aware nudge — "you wanted groceries done today and it's 1pm").

**Correction 5 — outbound Notion sync was missing an owner check.** `plugins/lists/src/notionSync.ts`'s `syncListItemToNotion` and `plugins/recipes/src/shoppingListFromMealPlanTool.ts`'s equivalent now both no-op unless `userId === notion.ownerUserId`, in addition to the existing `notion === undefined` no-op. Caught live: a second bigBrain account (`bb-test`, created purely for isolated testing) had its `add_list_item` call push straight into the real owner's Notion workspace — nothing was checking that the calling user was actually the one Notion workspace's designated owner. `notion.ownerUserId` was already used correctly on the *inbound* side (`notionReconcile.ts` always attributes adopted pages to it); this closes the same gap on the outbound side. A non-owner user's lists/list_items now stay Postgres-only, isolated by RLS same as everything else they write — this gateway remains one Notion workspace synced to one owning user, not one per household member, and non-owner accounts (test accounts, or future household members without their own Notion workspace) never leak into it.

**Addition — `lists.section_order` & `list_items.section` (store-layout ordering).** `lists` gains `section_order text[]` (default `'{}'`); `list_items` gains a nullable `section text`. A new `set_list_section_order(list_name, sections)` tool (`plugins/lists`) lets a list define its own ordering conversationally — e.g. one household's actual grocery-store aisle sequence, in the order they walk it — rather than a fixed enum or a one-off SQL script, since store layouts are arbitrary and stores rearrange constantly. Whenever an item is added to a list that has a section_order (`add_list_item`, and `generate_shopping_list_from_meal_plan` for meal-plan-generated groceries), it's classified into one of that list's own sections via a forced-schema LLM call bounded to that exact vocabulary (`classifySection.ts`, an `enum` in the tool's JSON Schema so the model can't invent a section that isn't there) — best-effort, same as Notion sync: a classification failure never blocks the item from being added, it's just left unsectioned. `get_list_items` then sorts by each item's position in its own list's section_order (computed in JS, not SQL, since a query spanning multiple lists at once — list_name is optional — would otherwise need a per-row-dependent ORDER BY); a list with no section_order, or an item with no classified section, falls back to creation order exactly as before this existed. Live-verified against a real 24-section grocery-store layout: items added out of order (`carrots`, `cheddar cheese`, `toilet paper`, `ice cream`) came back correctly sorted by aisle, with pre-existing unclassified items correctly sorting last. See `db/migrations/0007_list_sections.sql`.

**Addition — `recipes_meals` extension & `meal_plan_entries` (Phase 8.5: Recipes & Meal Planning).** `recipes_meals` (a `recipe_id`/`user_id`/`meal_name` stub since Phase 1) gains `ingredients jsonb`, `instructions jsonb`, `tags text[]`, `prep_time`/`cook_time`/`servings text`, `source_url text`. Ingredients stay flat strings (`"3 chicken breasts (300g/10oz each)"`) rather than decomposed quantity/unit/item fields — verified live against a real recipe site's own `schema.org/Recipe` structured data that even that spec doesn't decompose ingredient lines, so there's no reason bigBrain should either. Instructions preserve schema.org's optional section grouping (a plain string, or `{section, steps}` for recipes with labeled stages like "Sauce," "Assembly"). A new `meal_plan_entries` table (`plan_entry_id`, `user_id`, `recipe_id`, `planned_date`, nullable free-text `meal_label`) deliberately has no slot enum (breakfast/lunch/dinner) — the household's actual pattern is "usually just dinner, but Christmas has breakfast and lunch planned with no dinner," which a nullable label (null implies dinner) handles without rebuilding the parked Communications Gateway's calendar concept. See `db/migrations/0006_recipes_mealplan.sql`.

                                                                        **Addition — `documents`:**

                                                                        ```
                                                                        +-----------------------+
                                                                        |      DOCUMENTS         |
                                                                        +-----------------------+
                                                                        | PK | doc_id               |
                                                                        | FK | user_id               |
                                                                        ```

                                                                        Unlike every other table, `documents` is **not** canonical for its own content — the file at `file_path`, in git, is. This row exists purely so the LLM can find and summarize the document via chat. If a row and its file ever disagree, the file wins. `last_synced_sha` is the dedup key: re-ingestion only touches files changed since that commit, never the whole repo (§6's "additive sync" pattern applies here too).

                                                                        **Addition — `provider_credentials`.** Encrypted, DB-backed home for provider API keys that rotate more often than the rest of config (deepseek/openrouter LLM keys, the Voyage embeddings key, the Notion token). Household-wide system config, not per-user data — no `user_id` column, deliberately exempt from RLS like `users` itself; the only caller (the admin credentials route, `orchestrator/src/server/adminServer.ts`) already authenticates with a single household-wide admin key (`BIGBRAIN_ADMIN_API_KEY`), not a per-user one. `name` is a closed, fixed vocabulary (a `CHECK` constraint), not an open key-value store — a typo fails loudly instead of silently writing a row nothing reads. See `db/migrations/0008_provider_credentials.sql`.

                                                                        **Addition — `folders` / `chat_sessions` / `chat_messages` (native frontend chat history).** Backs the Chat tab's persisted history/folders once the native frontend (§5, Correction 7) needed its own chat storage. Deliberately normalized rows rather than Open WebUI's one-JSON-blob-per-chat shape (which that project is itself mid-migration away from) — and deliberately leaner than Open WebUI's own schema: no pinned/archived/tags/share columns, since household scale doesn't need them, and delete is a real delete. `chat_sessions.params` holds a fixed key set (system/temperature/top_p/max_tokens/model) merged over provider defaults at request time; `chat_sessions.tool_names` is null (all tools, the pre-existing default), `'{}'` (none), or an allow-list, filtered via `toolRegistry.ts`'s `filterToolRegistry`. `chat_messages.user_id` is denormalized for direct RLS, same precedent as `list_items`. See `db/migrations/0009_chat_sessions.sql`.

                                                                        **Addition — `orchestrator_settings`.** Small, DB-backed home for household-wide settings changeable from the Settings tab without a rebuild: the active named LLM connection profile and model (`io/llm/profiles.ts`'s `BIGBRAIN_LLM_PROFILES`), and the household's IANA timezone (`util/dateContext.ts`, so the LLM knows what day/time it actually is). Same shape as `provider_credentials` — household-wide, no `user_id`, RLS-exempt, closed `key` vocabulary — except values here are never secret, so they're stored and read back as plain text. See `db/migrations/0010_orchestrator_settings.sql`.

                                                                        **Addition — `chat_sync_points` / `chat_chunks` / `chat_memory_entries` / `household_memory`, plus `chat_sessions.parent_chat_id`/`fork_message_id`/`archived_at` (rolling chat summarization, recall, and branching).** Full design in `docs/chat-memory.md` — adapted from SillyTavern-Canonize's rolling-summarize/RAG pattern, reshaped around this platform's relational store already being the canonical world model (no lorebook needed) and its LLM-reasons-nothing-else principle (full-turn recall is an explicit tool call, `recall_chat_history`, never silently injected). Chat-lane RAG (`chat_chunks`) and a per-chat "key ideas" digest (`chat_memory_entries`, bounded via upsert on a model-chosen `topic_key`) are produced by `orchestrator/src/orchestrator/chatMemorySync.ts`'s poll loop, sequenced in core rather than a plugin because it needs `io/llm/callContext.ts`'s gate (`bb_principles.md` §14), which — like `runTurn`/`ToolRegistry` — isn't in the plugin-facing exports map. `household_memory` is the one cross-chat, cross-chat-surviving piece, populated once at explicit `archive_chat` (`bb_principles.md` §3: explicit signal, never an inactivity guess). Branching (`forkChat`, `io/chatSessions.ts`) is a new `chat_sessions` row constructed correct from birth rather than a divergence-detection system: unlike SillyTavern, bigBrain owns every mutation to its own `chat_messages`, so an edit/rerun's existing `truncateMessagesFrom` self-heals every derived table for free via a plain `on delete cascade` chain. See `db/migrations/0036_chat_sync_points.sql` through `0040_chat_branching.sql`.

                                                                        **Addition — `notes`.** Freeform notes for the Notes tab: a title and an unstructured content blob, `tags` informational-only (same non-triggering role as `lists.tags`). Deliberately distinct from `unstructured_notes` above rather than an extension of it — a `notes` row is a single piece of text a user or the LLM wrote and may come back to edit directly; `unstructured_notes` is write-once ingestion for semantic retrieval. Two tables now cover different jobs under the same English word, and nothing routes between them automatically — worth remembering when the next "note" request arrives, since which table it means isn't self-evident from the name alone. RLS-scoped like every other per-user table. See `db/migrations/0011_notes.sql`.

                                                                        **Addition — `prompt_presets`.** Reusable named system-prompt snippets for the Chat tab's per-chat settings pane. Picking a preset only copies its `content` into that chat's own `chat_sessions.params.system` — not a live reference; editing or deleting a preset later never changes a chat that already copied from it. RLS-scoped. See `db/migrations/0012_prompt_presets.sql`.

                                                                        **Addition — `chat_sessions.canvas_note_id` (Canvas).** The Chat tab's split-screen document panel, matching ChatGPT Canvas's own UX rather than the fenced-code-block or new-tab-type shapes considered and rejected first — a genuine tool-driven surface, not a text convention. Mechanism: `RegisteredTool` (`orchestrator/src/orchestrator/toolRegistry.ts`) gained an optional `focusHint(result): string | null` — a tool declares what's "canvas-worthy" about its own result, and `runTurn` (`orchestrator/src/orchestrator/loop.ts`) mechanically relays whichever id the last focus-hinting tool call in a turn returned (never interpreting it — bb_principles.md §2 holds), returning `{content, focusedNoteId}` instead of a bare string. `httpServer.ts` persists a non-undefined `focusedNoteId` to the chat's own `chat_sessions.canvas_note_id` (nullable FK to `notes`) — omitted entirely when a turn touches no note, so an unrelated turn never clears an existing focus. `create_note`/`update_note`/`get_note` (`plugins/notes`) are the only tools declaring `focusHint` today (`get_note`/`update_note` only when `found`, so a miss never focuses a nonexistent note) — deliberately plugin-driven rather than hardcoded to notes in the orchestrator, so a future unstructured-content plugin (email/doc drafting) can opt into the same mechanism without an orchestrator change. Frontend: `ChatView.tsx` renders `CanvasPanel` (`frontend/src/components/canvas/`) as a flex sibling of the chat pane whenever `activeChat.canvasNoteId` is set, splitting the space roughly 50/50; the panel re-fetches after every turn (unless the user has an unsaved local edit — `NoteEditor`'s own dirty guard) so it visibly updates as the LLM keeps editing. `NoteEditor` (`frontend/src/components/notes/`) is the shared title/content/save UI extracted out of `NotesView.tsx` so the Notes tab and Canvas's panel never diverge in behavior. The close button clears `canvas_note_id` via the existing `POST /v1/chats/:id` route; reopening a chat later brings its panel back automatically since focus is a real column, not client-only state. Deliberately scoped to `notes` only — no `status`/draft-vs-final flag was added anywhere; see `create_recipe`/`update_recipe`'s own note above (§6.5) for why structured domains (recipes, meal plans) still want a draft flag on their own row instead, not this mechanism, if that's ever built. See `db/migrations/0019_chat_canvas.sql`.

**Addition — per-chat connection override (`chat_sessions.params.profile`, built, no migration).** `chat_sessions.params` (§3 above, `chat_sessions`) gained a `profile` key alongside its existing `model` one — the Chat tab's per-chat settings pane can now pick a different named `BIGBRAIN_LLM_PROFILES` connection for one chat, not just a different model within the household's active one (`io/orchestratorSettings.ts`'s `active_llm_profile`, set from the Settings tab). No schema change needed since `params` is already an unconstrained `jsonb` column. Unlike the Settings-tab connection switch, this needs no restart: `httpServer.ts`'s `handleChatCompletions` builds a throwaway provider for the named profile via `createLlmProviderForProfile` (`io/llm/index.ts`) — the same mechanism the model-catalog preview (`listModelsForProfile`, `server/adminServer.ts`) already used for a read-only lookup, now reused to actually run the turn. A profile name that no longer exists in `BIGBRAIN_LLM_PROFILES` (stale override, since-removed connection) falls back to the household's active connection rather than failing the turn, logged per bb_principles.md §11.

**Addition — action dates & priority on `list_items`; reminder timestamps & lifecycle state on `notes` (built — db/migrations/0024_action_dates_priority.sql).** Extends the existing "time-blocked calendar event" primitive (`calendar_events`, §6.7) with the two other temporal primitives a household task queue actually needs, keeping both `list_items` and `notes` fully usable exactly as today for anyone who never sets either field — per household usage, not every list item or note is "an action," so none of this is mandatory.

- `list_items.due_at timestamptz` (nullable) — a target completion time, settable via `add_list_item` or the new `update_list_item` (`plugins/lists/src/updateListItemTool.ts`, addressed by `item_id`, same partial-patch shape as `update_note`). Paired with the existing `status`, this alone is the "Actionable Task Deadline" primitive: a `pending` item with a `due_at` in the past is overdue, no new status value needed.
- `list_items.priority text` (nullable, `CHECK (priority in ('P1','P2','P3'))`, unset treated as P2 for sorting) — same closed-vocabulary shape `list_items.status` and `provider_credentials.name` already use. Set explicitly at `add_list_item` time or changed later via `update_list_item`; never inferred or auto-assigned — Principle 3 applies directly, once a priority is set nothing in the system second-guesses it.
- `notes.reminder_at timestamptz` (nullable) — the "Contextual Review Alert" primitive: a prompt to open/review a note, not a deadline on the note itself. Settable at `create_note` time or via `update_note`; `update_note`'s own handler accepts `null` there specifically to let it be cleared (the LLM-facing tool schema only advertises `string`, since clearing-by-name isn't a real conversational case, but `NoteEditor.tsx`'s reminder field calls the same handler directly and does need to clear one).
- `notes.state text not null default 'active'` (`CHECK (state in ('active','pinned','archived'))`) — the lifecycle `notes` never had, now set via `update_note`. `pinned` surfaces a note in the Landing Deck's reference drawer (§5). `archived` hides a note from `get_notes`'s default browse but — same treatment as `documents.status = 'stale'`, §6.6, rather than deletion — stays fully reachable: a `search` term still matches an archived note even with no explicit `state` filter, and `state: 'archived'` browses them directly. Existing rows default to `active`; nothing changes for a note that's never pinned or archived.

**Addition — per-list `show_priority`/`show_due_dates` (built — db/migrations/0041_list_display_flags.sql).** The priority/due-date controls above were originally always rendered in the native frontend's Lists view for every list, whether or not that list ever uses them — a "Books to Read" list showed the same P1/P2/P3 picker and date field as a "Home Depot Run" list. `lists` gains two `boolean not null default false` columns, both off for every existing and new list until explicitly turned on, same opt-in shape as `section_order` (§ above). A new `update_list_settings(list_name, show_priority?, show_due_dates?)` tool (`plugins/lists/src/updateListSettingsTool.ts`, find-or-create + partial patch, same shape as `set_list_section_order`) flips them; `ListsView.tsx` renders the two checkboxes at the top of the selected list and hides/shows the priority select, due-date input, and their badges accordingly. These flags govern the specialist view's own controls only (Principle 5) — they never gate `list_items.priority`/`due_at` themselves, so a conversational "remind me to do X by Friday" still sets `due_at` on a list with the due-date toggle off, and turning a toggle off never clears or hides data that's already set on an item. Reading a list's own settings (as opposed to its items) needed a real "list of lists" read, which didn't exist before this — see the new `get_lists` tool (`plugins/lists/src/getListsTool.ts`), a direct read of `lists` rather than the item-derived name list `ListsBrowser.tsx` still uses for its own sidebar.

**Addition — `calendar_events.visibility`/`linked_list_item_id`/`linked_note_id` (built — db/migrations/0025_calendar_links_visibility.sql).** A `due_at`/`reminder_at` deliberately does *not* mirror into `calendar_events` automatically — that would need `list_items`/`notes` to keep a linked row in sync on every edit/delete, and neither plugin talks to Calendar's tables (no cross-plugin imports). Instead: a task or note deadline can be explicitly *promoted* to a real calendar event via `create_calendar_event`'s new `linked_list_item_id`/`linked_note_id` args (mutually exclusive), which just sets a one-directional pointer — `on delete set null`, same as `chat_sessions.canvas_note_id` (§3 above) — never kept in sync afterward. The promoted event becomes its own independent scheduling commitment: editing the task's `due_at` later doesn't move the calendar block, and rescheduling the block doesn't change the task's deadline.
- **Idempotent promotion:** a linked `create_calendar_event` call first checks for an existing event already linked to that same list item/note (scoped to the requesting user) and reuses it (`created: false` in the response) instead of inserting a duplicate. Needed because nothing else tracks "was this already promoted" — the frontend's "📅 Add to calendar" button has no local memory of a prior click, and re-clicking it (or the LLM calling the tool twice for the same deadline) would otherwise silently pile up duplicate events. An unlinked create is never deduplicated — a plain "Add" is always a genuinely new event.
- `visibility text not null default 'shared'` (`CHECK (visibility in ('private','shared'))`) gates only the outbound Google Calendar push (`googleOutboundSync.ts`) — a `'private'` row is exactly as visible in `get_calendar_schedule`/`CalendarView.tsx` as a `'shared'` one, it just never reaches the household's real Google Calendar. Default `'shared'` preserves the pre-existing behavior of every plain "Add" in `CalendarView.tsx` (still pushes to Google exactly as before); `create_calendar_event` separately defaults a *linked* event to `'private'` unless told otherwise, so promoting a task/note deadline doesn't flood the shared calendar with private to-do deadlines by default. `update_calendar_event` can flip it either way — private → shared mints a Google mapping for a row that was never pushed; shared → private pulls it back off Google and drops the now-stale `calendar_google_sync_map` row, so a demoted event doesn't linger there.
- Frontend: `CalendarView.tsx` rows are now click-to-expand (were static `<li>`s) — expanding shows `description`/`assigned_members` (both existed in the data already but were never rendered), a visibility toggle button for non-read-only events, and — when `linked_note_id` is set — an "Open linked note" toggle that renders `NoteEditor` inline, same pattern `PinnedNotesDrawer.tsx` already uses. `NoteEditor.tsx` and `ListsView.tsx` each gained a "📅 Add to calendar" button (shown only when `reminder_at`/`due_at` is set) that calls `create_calendar_event` with the corresponding link field — the only way a promotion actually happens today; there's no LLM-driven "put this on the calendar" flow yet, though nothing stops the model from calling `create_calendar_event` with a link arg the same way.

**Addition — composite sort: time bucket first, priority second (designed, not yet built).** Deliberately simpler than a priority-major hierarchy: the primary key is always the temporal bucket, priority only breaks ties within a bucket. This keeps the ranking legible — what's overdue always outranks what's merely important — and avoids the failure mode of a priority-major scheme, where an upcoming P1 could crowd out an already-overdue P2, exactly backwards for a household task queue.

1. Compute each item's bucket from `due_at`/`reminder_at` against the household's configured timezone (`util/dateContext.ts`, the same helper `TodayAgenda.tsx`'s `isoDateInZone` and `getCalendarScheduleTool.ts`'s default range already use): **Overdue → Due Today → Upcoming → Undated.**
2. Within a bucket, sort by priority: **P1 → P2/unset → P3.**
3. Within a bucket+priority pair, break ties by proximity: overdue sorts most-overdue-first (oldest `due_at` first), due-today/upcoming sort soonest-first, undated sorts newest-created-first, falling back to a list's own `section_order` where that's set — same fallback `get_list_items` already applies today when nothing else distinguishes two items.

A pure function (Principle 8) would compute this bucket+priority+proximity key from a row alone — never LLM-judged, the same shape as `sectionRank` in `getListItemsTool.ts`'s existing precedent, not a new reasoning surface. Not yet built: `get_list_items` itself stays section-order sorted (unchanged) now that it also carries `priority`/`due_at` as plain columns; this ranked view is specifically the Landing Deck's Tier 1 action queue's job (§5), which doesn't exist yet either.

                                                                        ### 4. THE AGENTIC INTERACTION LOOP

                                                                        Two additions to the v1 loop: an optional **write-time hint** and an optional **read-time render tick**. Both are additive to the default conversational path, never required.

                                                                        ```
                                                                        User App                Server                 Cloud LLM              Local Tool / DB / Notion
                                                                           |                       |                       |                          |
                                                                              |--(1) Text + optional--+                       |                          |
                                                                                 |    write-time hint    |                       |                          |
                                                                                    |    (shopping/event/   |--(2) Forward + hint---+                          |
                                                                                       |    recipe/note/email) |    weights classifier |                          |
                                                                                          |                       |                       |--(3) Classify + reason--+
                                                                                             |                       |<--(4) Tool call--------|                          |
                                                                                                |                       |--(5) Execute + scope---+------------------------->|
                                                                                                   |                       |    to user_id (RLS)    |                          |
                                                                                                      |                       |<--(6) Raw result------+--------------------------|
                                                                                                         |                       |--(7) Forward result---+                          |
                                                                                                            |                       |<--(8) Chat reply------+                          |
                                                                                                               |<--(9) Render reply + [optional: read-time render tick →                  |
                                                                                                                  |    optional Notion    |  deep-linked Notion hop, if domain has a mirror]|
                                                                                                                     |    hop link            |                       |                          |
                                                                                                                     ```

                                                                                                                     - **Write-time hint** (tickbox: shopping / event / recipe / note / email) weights the classifier at step 3. Absence of a hint falls back to pure inference (vector + structured signal, arbitrated by the LLM) as previously scoped.
                                                                                                                     - **Read-time render tick**, if present, tells the server which domain's Notion mirror (if any) to deep-link to, rather than asking the LLM to guess a presentation shape. Default is always plain chat.
                                                                                                                     - **Tag-browse fallback** (not shown above) bypasses the LLM and hits Postgres directly: `WHERE pinned_tags @> ARRAY[...]`. This exists for the case where inference — with or without a hint — still isn't returning what the user wants.

                                                                                                                     ### 5. INTERFACE & RENDERING MODEL

                                                                                                                     - **Default:** conversational markdown, always. No user action is ever only visible via a specialist surface.
                                                                                                                     - **Specialist surfaces:** shopping lists, calendar, recipes — domains with a natural tabular/board shape — get a Notion mirror. Raw notes stay chat/vector-only; there is no natural "specialist view" for them and none is planned.
                                                                                                                     - **Sync direction:** two-way, but Notion is never trusted. Inbound webhooks are treated as untrusted external writes, identical in kind to an inbound email — parsed via the same deterministic/LLM-assisted pipeline, matched to a `user_id` and row via `notion_sync_map`, never inferred from payload content.
                                                                                                                     - **Hop button:** server-constructed, view-scoped Notion deep link (e.g. filtered to unchecked shopping items), not a static workspace link. Always presented alongside a chat confirmation, never in place of one.

                                                                                                                     **Source vs. mirror — not symmetrical, and GitHub is two different things depending on the repo.** Notion and GitHub sit on opposite sides of the canonical relational store in general, but "GitHub" isn't one relationship:
                                                                                                                       - **Notion is a mirror.** Postgres data flows *out* to it. Notion is reconstructible; if wiped, it's rebuilt from Postgres.
                                                                                                                         - **Each user's local content repo is the platform's own storage, git-backed.** It's not a foreign integration — it's where authored/clipped documents canonically live, per §3's `documents` table design. The platform is permitted to write here, deliberately and only on explicit user action (e.g. a chat-initiated "save this to docs" or "clip this page"). It never authors or edits a doc autonomously. **Deliberately local and per-user, never `bigBrain`'s own source repo and never one repo shared across users** (§6.6): there's no remote and no credential to leak, and filesystem separation keeps one user's content unreachable from another's, matching the RLS isolation every other table already gets.
                                                                                                                           - **Any other repo (application code, unrelated projects) is a true external source.** Read-only, same as before — the platform has no more business writing there than it does in someone else's Notion workspace.

                                                                                                                             The distinction that matters isn't "GitHub vs. not GitHub" — it's **platform-owned storage vs. external system**, regardless of which host it happens to sit on. Write scope is granted per-repo, not per-service.

**Addition — the Open WebUI integration boundary.** Open WebUI (the chosen interface layer, Phase 4) ships a lot of its own extensibility surfaces beyond being a chat window. Deciding which of those to actually use came down to one question per feature: does it own a second copy of bigBrain's data, or is it just UI/text? The former is rejected regardless of how convenient it looks; the latter is fair game.

*Using:*
- **The chat UI itself** (streaming, markdown, mobile layout, history, search) — no reason to rebuild or fork something already good.
- **Models connection** (`/v1/models` + `/v1/chat/completions`) — the core integration since Phase 4.
- **Trusted-header SSO** (`WEBUI_AUTH_TRUSTED_EMAIL_HEADER`, Cloudflare Access) — no second password beyond the household's existing Google OAuth.
- **Tools, via an OpenAPI tool-server connection** (`orchestrator/src/server/openApiToolServer.ts`): `GET /v1/tools/openapi.json` (a spec generated mechanically from the existing `ToolRegistry` — every tool's JSON-Schema `parameters` already *is* an OpenAPI request-body schema) plus `POST /v1/tools/:name`, authenticated identically to chat completions, bypassing `runTurn` entirely — the external caller's own model already decided which tool and with what arguments. Chosen over Open WebUI's native **MCP** support specifically because Open WebUI's own docs describe MCP as admin-gated and running "inside Open WebUI's trust boundary with the connecting user's full scope" (stateful, capable of host command execution over its transport) — heavier than bigBrain's stateless, already-scoped action set needs. OpenAPI tool servers are Open WebUI's own stated preferred path "for most deployments."
- **Skills** (verified against the actual running backend, `open_webui/models/skills.py` / `utils/middleware.py`, not just docs): a named block of reusable plain-text `content`, with no execution and no external call — the opposite kind of thing from a Tool. Either explicitly mentioned inline (`<$skillId|label>`, pulling the full `content` into that turn) or attached to a model's own metadata (`skillIds`), in which case every conversation with that model gets a short `<available_skills>` listing (id/name/description only) so the model can reach for one without the full content costing tokens on every turn. Used to hold reusable procedural guidance (e.g. a meal-planning workflow: check `get_recipes` before proposing a plan, don't repeat a meal within N days, offer to generate a shopping list afterward) attached to bigBrain's own model connection — modular behavioral guidance, not baked permanently into one giant system prompt.
- **Folders' system-prompt field** — cheap, per-context text injection, no data-ownership question.

*Not using, and why:*
- **Knowledge** (Open WebUI's own file/RAG store) — a second, separate embedding store. Using it means either duplicating notes into an unsynced second copy, or running two independent retrieval passes stacked on top of each other. `unstructured_notes`/`documents` (§6.1) stay the one source of truth.
- **Notes** (Open WebUI's own built-in note-taking) — same problem as Knowledge: a second place notes could live, disconnected from `ingest_note`. Real notes go in via chat.
- **Calendar, Channels** (newer Open WebUI features) — Calendar would duplicate the native household calendar (§6.7, previously the parked Communications Gateway at old §6.3); Channels is team-chat, not relevant at household scale.
- **Open Terminal** (newer Open WebUI feature) — real host/terminal access from a chat UI. Flagged explicitly to stay off regardless of version; a genuine risk surface, not a knob to enable casually.

*Considered and rejected: forking Open WebUI.* Forking means owning its entire codebase going forward (its RAG pipeline, its own auth/migration system, its admin panels) for the ~10% actually used, permanently welding the interface layer to one upstream project's internals — the opposite of "Interface Layer is Replaceable" above. A minimal from-scratch frontend was also considered and shelved for the same reason in spirit: the existing chat UI is already good, and the actual pain point (no onboarding, generic suggested prompts) has a much cheaper fix — custom Prompts — than rebuilding a chat interface from zero.

**Correction 7 — the "no custom frontend" call above was reversed; a native frontend now exists alongside Open WebUI.** `frontend/` (Vite + React, no relation to Open WebUI) is a second, parallel interface: a browser-tab-style UI (`TabStrip`/`useTabs.ts`) holding a chat tab plus native specialist views — Lists, Recipes, Meal Plan, Notes, Settings, chat History — each calling tools directly through the same `/v1/tools/:name` surface via a hand-written `callTool` client (`frontend/src/api/client.ts`), never through Open WebUI. Open WebUI is unaffected and still holds the Models/Tools connection described above; this is additive, not a replacement.

This reverses the "considered and rejected" call directly above without ever amending it — worth recording since it's exactly the kind of drift this spec exists to prevent. The stated reasons for shelving a custom frontend (chat UI already good; the real pain point was onboarding, fixable cheaper via Prompts) evidently stopped holding once specialist domains needed something Open WebUI's rejected Knowledge/Notes features couldn't provide without becoming "a second copy of bigBrain's data" — a native tab reads/writes the same tool surface as chat, so it never does. Backing tables: `folders`/`chat_sessions`/`chat_messages` (chat tab) and `notes` (Notes tab) — see §3 additions. This also makes the line above — "Specialist surfaces: shopping lists, calendar, recipes... get a Notion mirror" — stale: recipes (§6.5) and calendar (§6.7) both ship as native frontend tabs instead, and lists is now doubly-surfaced (Notion mirror *and* a native tab). A Notion mirror is no longer the default for a new specialist domain; a native tab is, with Notion reserved for domains that specifically benefit from being visible outside bigBrain's own frontend.

                                                                                                                                   Corrected query — `days_between_purchases` does not exist as a stored column; it's derived via window function before aggregation:
                                                                                                                                   ```sql
                                                                                                                                   WITH deltas AS (
                                                                                                                                     SELECT
                                                                                                                                         item_name,
                                                                                                                                             timestamp - LAG(timestamp) OVER (
                                                                                                                                                   PARTITION BY item_name ORDER BY timestamp
                                                                                                                                                       ) AS days_between
                                                                                                                                                         FROM shopping_logs
                                                                                                                                                           WHERE user_id = $1
                                                                                                                                                           )
                                                                                                                                                           SELECT item_name, COUNT(*), AVG(days_between)
                                                                                                                                                           FROM deltas
                                                                                                                                                           GROUP BY item_name;
                                                                                                                                                           ```

                                                                                                                                                           #### 6.4 Notion Sync Gateway *(built, revised from the original sketch below during Phase 8)*
                                                                                                                                                           Syncs `list_items` (the generic `lists`/`list_items` primitive, not `shopping_logs`/`recipes_meals`/calendar tables — those either don't exist yet or were deliberately never wired to Notion) into one Notion database ("bigBrain Lists": `Item`/`List`/`Done`/`Completed At` properties), scoped to one Notion workspace tied to one owning bigBrain user (`BIGBRAIN_NOTION_OWNER_USER_ID`) — not a separate workspace per household member.

                                                                                                                                                           - **Outbound** (`orchestrator/src/io/notion.ts`, `plugins/lists/src/notionSync.ts`): `add_list_item`/`complete_list_item` push to Notion right after their Postgres write succeeds — best-effort, never fails the tool call if Notion is unreachable. Mint-and-stamp identity, same trust model as CNZ: `notion_sync_map` is the only place a `list_items` row is linked to a Notion page, keyed by `(source_table, source_row_id)`; first sync creates the page and mints the mapping, later syncs update the existing page by looked-up `notion_page_id`. Rate-limited to Notion's ~3 req/sec via a simple serializing throttle, not a durable queue — an unsynced write during a process restart just stays unsynced until the next edit touches that row.
                                                                                                                                                           - **Inbound** (`plugins/lists/src/notionReconcile.ts`): **polling** (~30s), not webhooks — despite Notion's webhook system existing and being confirmed available, polling avoids exposing a new public inbound route (the orchestrator accepts zero unauthenticated inbound traffic) and avoids webhook payload signature verification, for a household-scale feature where the delay is imperceptible. Adopts **only** a page's Done/Completed-At state into Postgres — never its Item/List (name) properties, which stay authoritative in Postgres; renaming in Notion is simply overwritten by the next outbound push. A page with no matching `notion_sync_map` row (typed directly into Notion, not yet tracked) is adopted as a brand-new item, attributed to the owning user — this is deliberately different from CNZ's orphan-*purge* pattern, since here an "orphan" is a legitimate new item, not stale state to discard.
                                                                                                                                                           - **Reconciliation / the race that was actually caught live:** Postgres always wins on divergence — no LLM-guessed merges. Outbound sync creates the Notion page, *then* inserts `notion_sync_map` — a real window exists between those two steps where an inbound poll landing in it sees the brand-new page as unmapped and would otherwise adopt it a second time, producing a duplicate `list_items` row for one Notion page. Fixed with a unique constraint on `notion_sync_map.notion_page_id` (`db/migrations/0005_notion_sync_map_page_unique.sql`) plus per-page transactions in the reconciliation poll (not one transaction for the whole batch), so a conflict on one page is logged and skipped without rolling back everything else that poll would have reconciled.

                                                                                                                                                           #### 6.5 Recipes & Meal Planning *(built)*
                                                                                                                                                           Eight tools (`plugins/recipes`), no Notion surface of their own — meal-plan-generated groceries ride the existing `lists`/`list_items` primitive and its Notion sync (§6.4) rather than getting a separate gateway.

                                                                                                                                                           - **`import_recipe(url | raw_text)`:** cheap-and-precise before expensive-and-fuzzy, same ordering as the write-time hint/inference fallback elsewhere. A `url` is fetched and checked first for embedded `schema.org/Recipe` JSON-LD (`plugins/recipes/src/schemaOrgRecipeParser.ts`) — the same structured data virtually every serious recipe site embeds for Google's rich-snippet requirement, verified live against a real page's actual markup rather than assumed from the spec. Only when that's missing or incomplete (or when `raw_text` was given directly, e.g. a pasted recipe with no source page) does it fall back to a forced-schema LLM extraction call (`extractRecipeWithLlm.ts`, mirroring `classifyNote.ts`'s pattern exactly).

                                                                                                                                                           **Addition — `create_recipe` / `update_recipe`.** `import_recipe`'s `raw_text` path always pays for a forced-schema LLM extraction call, which is the right trade when the source is genuinely unstructured (a pasted page, scraped text) but wasteful when the *conversational* LLM has already worked out a recipe's fields with the user turn by turn — it would have to flatten its own structured reasoning to prose just to pay a second, lossier call to re-derive the same structure. `create_recipe` takes `mealName`/`ingredients`/`instructions`/`tags?`/`prepTime?`/`cookTime?`/`servings?` directly from the caller and inserts them as-is (`source_url` stays null — nothing was fetched), reusing `recipeSchema.ts`'s `isParsedRecipe` so it never validates the shape differently than `import_recipe` does. `update_recipe` is the same partial-patch shape as `update_note`/`update_calendar_event` — only supplied fields change, addressed by `recipe_id` (not `meal_name`, so an in-progress rename can't collide with `get_recipe`'s fuzzy match) — enabling the "progressively build and edit a recipe in conversation" case `import_recipe` alone couldn't cover. Deliberately scoped to unstructured→structured recipe authoring only; no `status`/draft-vs-final concept was added to `recipes_meals` — see the Canvas drafting-workspace discussion for why structured domains want a draft flag on their own row rather than a text-sandbox detour, if and when that's actually built.
                                                                                                                                                           - **`get_recipes` / `get_recipe`:** list-summary and full-detail reads, matched by case-insensitive name like every other chat-facing lookup in this platform (`findOrCreateList`, `complete_list_item`).
                                                                                                                                                           - **`add_meal_plan_entry` / `get_meal_plan`:** application-level upsert on `(user_id, planned_date, meal_label)` — replanning a date replaces rather than duplicates, but two different labels on the same date (the Christmas case) coexist deliberately.
                                                                                                                                                           - **`generate_shopping_list_from_meal_plan`:** aggregates ingredient strings across every recipe planned in a date range, dedupes case-insensitively (no quantity math/unit conversion — `list_items` has no quantity column, and unit arithmetic is exactly the kind of complexity this project keeps deciding to punt on, per the lists-vs-inventory decision above), skips ingredients already pending on the target list, then writes through the same find-or-create-list-and-sync-to-Notion primitive `plugins/lists` uses.                                                                                                                                                            #### 6.6 Document Repository & Web Clipping *(built — local per-user git, no remote; offsite backup not yet built)*
                                                                                                                                           Originally scoped as a "GitHub Ingestion Gateway" watching bigBrain's own repo for externally-authored changes; reopened and rebuilt while designing web clipping (a page turned into a readable document, not just a search-indexed note, §6.1). Two changes from that original sketch survived into the build: content lives outside `bigBrain`'s own source repo entirely (§5), and the direction is outbound-first (bigBrain authoring/clipping content) rather than watching an externally-edited repo. A third emerged only once "separate repo" was actually designed: rather than one shared GitHub repo (a write credential for which could leak content across household members and bypass the RLS isolation `documents` otherwise gets), each user gets their own local git repository with no remote at all — filesystem separation naturally matches RLS instead of depending on a credential's scope, and there's no PAT/token to leak in the first place.

                                                                                                                                           - **Schema:** `documents` (§3) gained the columns the pipeline actually needed (`title`, `created_at`, `updated_at` — `db/migrations/0020_documents_title.sql`, mirroring `notes`' exact shape including its `(user_id, updated_at desc)` browse index) on top of what already fit unmodified (`repo`/`file_path`/`last_synced_sha`/`vector_embed`/`summary_short`/`status`). `repo` holds a per-user label (`local/<user_id>`), not a real remote. `documents` stays not-canonical for its own content; the file in the user's repo is (§5).
                                                                                                                                           - **Git mechanism (`plugins/documents/src/gitRepo.ts`):** one working repo per user under `BIGBRAIN_DOCUMENTS_DIR/<user_id>` (default `/app/content`, on its own named Docker volume — `docker-compose.yml`'s `bigbrain-documents` — so a rebuild doesn't wipe it). `git` runs via `execFile` (argv array, never a shell string, since commit content can be LLM-influenced) with a local-only `user.name`/`user.email` set on first init; writes are serialized per user (a promise-chain queue, same shape as Notion sync's rate-limit throttle, §6.4) so two saves for the same user never race the same working tree, while different users' repos run fully independently. A caller-supplied `path` is resolved and checked against the user's own repo root before any write, so it can never escape into another user's tree or the host filesystem.
                                                                                                                                           - **Write path:** `save_document(title, content_markdown, path?)` (`saveDocumentTool.ts`) — same call shape as `create_note`/`create_recipe`. `ingest_url(url)` (`ingestUrlTool.ts`) is the web clipper: `fetchUntrustedUrl` (already SSRF-guarded — the `import_recipe` precedent, §6.5) → `htmlToMarkdown.ts` (`@mozilla/readability` strips nav/ads/boilerplate and keeps the article, the same library Firefox's own reader view uses; `turndown` converts what's left to real Markdown — headings/links/lists survive, unlike `plugins/recipes/src/htmlToText.ts`'s crude LLM-fallback stripper) → the same shared save sequence (`saveDocument.ts`): commit to git, summarize (`classifyDocument.ts`, a `summary_short`-only forced-tool call mirroring `classifyNote.ts`) and embed, then upsert `documents` keyed on `(repo, file_path)` so re-saving a title updates the existing row instead of duplicating it. Both tools are user-initiated (a chat turn asking to save/clip something), matching §5's "permitted to write here, deliberately and only on explicit user action — never autonomous authoring."
                                                                                                                                           - **Read path:** `get_document(doc_id)` / `list_documents(search?)` (metadata-only listing, full content only once picked — same split as `get_notes`/`get_note`), plus a read-only `DocumentsView` (`frontend/src/views/DocumentsView.tsx`) — no edit surface in-app, since the file is canonical and git is the edit surface (§5); rendered with the same `ReactMarkdown`/`remark-gfm`/`remark-breaks` setup `ChatView.tsx` already uses for chat bubbles. Includes its own "clip a URL" quick action calling `ingest_url` directly — moving/displaying data, not reasoning about it (§2), same as any other tool-backed UI control in this app.
                                                                                                                                           - **Auth:** none — no credential, no `provider_credentials` entry, no migration for one. Removed entirely by going local-only; see the superseded sketch below for the GitHub-PAT version this replaced before anything was built against it.
                                                                                                                                           - **Offsite backup: built (`backup/`, a standalone sidecar in `docker-compose.yml`), closing the gap this section used to flag.** Exactly the whole-stack-in-one-mechanism shape anticipated below: nightly `pg_dump` of the entire database plus a tar of every user's `bigbrain-documents` content repo plus `secrets.enc.env`, bundled and `age`-encrypted before leaving the host, pushed to an S3-compatible bucket (Cloudflare R2 today; the mechanism is provider-agnostic — see `backup/backup.sh`). The `age` private key that can read a backup back out is deliberately never on this host, same custody model as the key that decrypts `secrets.enc.env` (`docs/bootstrap.md`). Restore procedure: `backup/README.md`. Retention is an R2 object-lifecycle rule (Cloudflare dashboard), not code in this repo. `bigbrain-pgdata` and `bigbrain-documents` now share the same offsite durability instead of neither having any, as originally flagged.
                                                                                                                                           - **Chunking: built.** `saveDocument.ts` now splits a document via `chunkDocument.ts` — walking the Markdown's own heading structure (real headings survive the htmlToMarkdown.ts/turndown clip), with a heading breadcrumb prefixed to each chunk and oversized sections packed further along paragraph boundaries up to a plain character-count cap (no tokenizer dependency exists anywhere in this repo, so the cap is an approximate ~750-token heuristic, not a precise count). Each chunk gets its own embedding in a new `document_chunks` table (chunk text, `vector_embed`, `ordinal`, `heading_path`, `doc_id` FK, cascades on document delete), replaced wholesale on every re-save rather than diffed. `search_documents` ranks chunks by cosine distance (pgvector's `<->`) against the embedded query — the first thing in bigBrain that actually reads a `vector_embed` column back; the whole-document embedding on `documents` itself, and the identical pattern on `unstructured_notes`, are still written on every save but still never queried. No `ivfflat`/`hnsw` index yet — household-scale row counts don't need one, a sequential scan is fine, and one can be added later without any application-code change.

                                                                                                                                           - **Tags and lexical search: built.** Each chunk is auto-tagged at save time (`classifyDocument.ts`'s `tagChunks`, fed the user's existing tag vocabulary as a nudge toward reuse rather than inventing near-duplicates like "cooking" vs "recipes" — a nudge, not a guarantee; tags are inexact by nature, same tolerance already extended to `unstructured_notes`' `auto_tags`, which has run with zero vocabulary awareness at all). `document_chunks.tags` (`text[]`, GIN-indexed) backs both a filter (`list_documents`/`search_documents`'s `tags` param, array-overlap `&&`) and `list_document_tags` (sources the picker in `DocumentsView`). Separately, `list_documents`' `search` param was upgraded from a plain `title`/`summary_short` `ILIKE` to ranked full-text (`tsvector`/`ts_rank`) over `document_chunks.heading_path`/`content` — this app's search box, deliberately lexical rather than semantic: a short, deliberately-typed query doesn't give an embedding model enough to work with the way `search_documents`' fuller chat-message queries do, so the box and the chat tool intentionally use different ranking strategies. Heading matches outrank body-text matches (`setweight` 'A' vs 'B'). No vocabulary-consolidation job exists (or is planned unless drift actually shows up in practice) — bigBrain already has a background-job mechanism per plugin (`calendar/icsSync.ts`, `lists/notionReconcile.ts`) that could host one later.
                                                                                                                                           - **Pretty clips: built.** `htmlToMarkdown.ts` gained three passes around the existing Readability/Turndown conversion, all deterministic (no LLM call, unlike everywhere else this app enriches saved content): (1) `extractMetadata` reads Schema.org JSON-LD, OpenGraph, and a plain `meta[name=author]` tag, falling back to Readability's own `byline`/`siteName`/`publishedTime` — deterministic sources first, the same "reuse before inventing" instinct already applied to tag vocabulary. (2) every `img`/`a` `src`/`href` is resolved to an absolute URL via `new URL(attr, sourceUrl)` before Readability runs, closing the previously-known relative-link limitation. (3) `normalizeHeadings` remaps whatever heading levels a site misused for styling so the shallowest one becomes H3 (nesting under `DocumentsView`'s own `<h2>` title) with no gaps, skipping fenced code blocks so a `#`-prefixed code comment is never touched. Metadata flows two places: a YAML frontmatter block (`saveDocument.ts`) prepended only to the string written to git — never to the string `chunkDocument`/the doc-level embedding see, so frontmatter can never pollute a chunk or its embedding — and new `documents.source_url/site_name/author/published_at` columns (`0023_document_source_metadata.sql`) for structured access, rendered as a one-line byline under the title in `DocumentsView`. `save_document`'s manual path never sets `metadata`, so it's unaffected: no frontmatter, all four columns stay null. Evaluated and explicitly scoped out: headless-browser rendering (real SSRF-surface and dependency cost for a household-scale tool, revisit only if a specific SPA/paywall clip actually fails), local image asset caching (would make the per-user git repo start owning binary storage, worsening the already-flagged offsite-backup gap), callout-box/layout-table detection (fragile heuristics, niche payoff), and any LLM pass that rewrites body text rather than annotating it (in tension with every other enrichment in this app leaving canonical content untouched). Code-block language detection needed no work — Turndown already reads `language-xxx` off the `<code>` element's class.

                                                                                                                                           #### 6.7 Household Calendar *(built — Cozi/Outlook read-only ICS, native events, and bidirectional Google Calendar OAuth sync)*
                                                                                                                                                           Native calendar, aggregating read-only external feeds, AI/user-created events, and a genuinely two-way Google Calendar mirror into one Postgres table — no Notion mirror (unlike §6.4), following the §6.5 precedent that a domain gets a native in-app view instead of a Notion surface when one isn't needed.

                                                                                                                                                           **Addition — bidirectional Google Calendar sync (`db/migrations/0017_calendar_google_ics.sql`, `0018_google_calendar_oauth.sql`).** Originally scoped, then actually shipped, as a read-only ICS feed (Google's "Secret address in iCal format," same shape as Cozi's) — superseded before deployment once real two-way sync was requested instead, since running both mechanisms against the same `source = 'google'` value would fight each other. `orchestrator/src/io/googleCalendar.ts` is the API client (mirrors `io/notion.ts`'s optional, best-effort factory shape); `plugins/calendar/src/googleSync.ts` is the inbound poll (every 5 min, via Google's incremental `syncToken`, not ICS re-parsing) and `googleOutboundSync.ts` is the outbound push, called from `create_calendar_event`/the new `update_calendar_event`/`delete_calendar_event` tools (added specifically because real bidirectional sync needs edit/delete parity — this is the "real use" the original deferral was waiting for). OAuth scope is `calendar.events` (not the broader `calendar`, which also grants calendar-list/ACL management bigBrain doesn't need).
                                                                                                                                                           - **Identity:** `calendar_google_sync_map` (`0018_google_calendar_oauth.sql`), shaped like `notion_sync_map` (§6.4) but a strict 1:1 on `calendar_events.event_id` — the only place a row is linked to a Google event id, for both directions (a native row pushed out, or a Google-originated row pulled in). `unique(google_event_id)` is applied from day one rather than after a live race, pre-emptively closing the exact outbound-insert-then-mint-mapping window Correction 5 caught for Notion.
                                                                                                                                                           - **Conflict rule:** plain last-write-wins by timestamp (Google's `updated` vs. `calendar_events.updated_at`) — no merge logic, same "no LLM-guessed merges" stance §6.4 already takes for Notion. A row where local is newer than what a poll saw from Google is left alone, not overwritten.
                                                                                                                                                           - **Inbound deletes:** unlike Notion sync (never deletes `list_items` inbound — an "orphan" there is always a legitimate new item), a Google event reporting `status: 'cancelled'` *does* delete the local row — genuine two-way delete propagation, new territory for this codebase.
                                                                                                                                                           - **The one unauthenticated inbound route this system has ever needed:** `GET /v1/admin/google-calendar/callback` (`server/httpServer.ts`/`adminServer.ts`) receives Google's OAuth redirect, which is a plain browser GET with no way to carry a bearer token or Access header. It isn't gated by `isAdminAuthorized` like every other `/v1/admin/*` route; instead it's protected by a single-use `state` nonce (`mintGoogleOauthState`/`consumeGoogleOauthState`, in-memory, TTL-bounded) minted only for an already-admin-authorized `auth-url` request — this route can only ever complete a flow the server itself started, never accept an arbitrary inbound payload the way a real webhook would. Documented as a deliberate, narrow exception to §6.4/Correction 6's "zero unauthenticated inbound traffic," not a reversal of it.
                                                                                                                                                           - **Credentials/settings:** `google_calendar_client_secret`/`google_calendar_refresh_token` are secrets (§12, `provider_credentials`) — the refresh token alone grants ongoing read/write access to the household's calendar. `google_calendar_client_id`/`google_calendar_owner_user_id`/`google_calendar_id`/`google_calendar_sync_token` are not (§13, `orchestrator_settings`) — an id is a selector, a sync token is a bookmark, neither grants access on its own.
                                                                                                                                                           - **Out of scope for this pass:** recurring-event (`RRULE`) editing semantics (single-instance vs. whole-series) — native bigBrain events have no recurrence concept; a Google-originated recurring event is handled as Google's own expanded instances, same as the old ICS approach, not editable as a series from bigBrain. Also out: attendees/invites, multiple Google calendars per household, per-household-member Google accounts.
                                                                                                                                                           - **External setup (human, not automatable):** a Google Cloud project with the Calendar API enabled; an OAuth consent screen left in Testing mode with the household's own Google account added as a test user (`calendar.events` is a "sensitive," not "restricted," scope — Testing mode works indefinitely with no Google verification review, though this is worth reconfirming against Google's current console since policy specifics do shift); an OAuth 2.0 Web-application client with redirect URI `https://<public-base-url>/v1/admin/google-calendar/callback`. The resulting client id/secret are entered in the Settings tab's Google Calendar fieldset, then "Connect Google Calendar" drives the actual consent flow.

                                                                                                                                                           - **Schema (`calendar_events`):** `source` enum (`'cozi' | 'outlook' | 'google' | 'native'`, `'google'` widened in `0017_calendar_google_ics.sql`), `external_id` (feed UID for `cozi`/`outlook`, Google's own event id for `google`, unique per source), `user_id` (required, RLS-scoped exactly like `list_items` — see below), `title`/`description`/`location`/`start_time`/`end_time`/`all_day`, `assigned_members text[]` (informational household-member tags, same role as `lists.tags` — never a security boundary; `user_id` is). `color_code`/`is_read_only` are *not* stored columns — both are pure functions of `source`, computed at read time (`plugins/calendar/src/sourceMeta.ts`), so there's exactly one place that knows what a source means, per the canonical-record principle. `'google'` is `isReadOnly: false` — unlike `cozi`/`outlook`, it's a genuine two-way row editable via `update_calendar_event`/`delete_calendar_event` like any other. `visibility`/`linked_list_item_id`/`linked_note_id` (`0025_calendar_links_visibility.sql`) — see the §3 addition above.
                                                                                                                                                           - **Ownership for shared feeds:** Cozi is one shared `.ics` URL, not per-member — same shape as Notion's single-workspace sync, attributed to one owning user via `calendar_owner_user_id` (mirroring `BIGBRAIN_NOTION_OWNER_USER_ID`, §6.4). Google Calendar has its own separate owning user (`google_calendar_owner_user_id`) rather than reusing `calendar_owner_user_id` — the two connections (ICS feeds vs. OAuth) are independent and either can be configured without the other. Outlook (work) and native events are already tied to whichever user's tools created them.
                                                                                                                                                           - **RLS:** `calendar_events` gets the same `user_scoped` policy as `lists`/`list_items` (`db/migrations/0004_lists.sql`) — `user_id = app_current_user_id()`, enabled and forced. No table in this system is exempt from Principle 4, and a household calendar with "assigned members" is exactly the kind of table where it'd be tempting to substitute the tag array for real scoping; it doesn't.
                                                                                                                                                           - **Ingestion (`plugins/calendar/src/icsSync.ts`):** internal scheduled job, not an HTTP route — the orchestrator accepts zero unauthenticated inbound traffic (§6.4, Correction 6), so this is a poll, not a webhook receiver. Cadence ~30 min (unlike Notion's ~30s reconcile — ICS feeds don't need near-real-time, and Cozi/Outlook publish on their own schedule regardless of poll frequency). Recurring events (`RRULE`) expanded 90 days out at parse time. Upsert on `(source, external_id)`.
                                                                                                                                                           - **Privacy masking:** `BIGBRAIN_MASK_WORK_CALENDAR` env flag; when set, the Outlook parser (a pure function, `plugins/calendar/src/parseWorkEvent.ts`) replaces `title`/`description`/`location` with a fixed placeholder before the row ever reaches Postgres. Config-driven, not LLM-judged — this is redaction, not reasoning, so it doesn't touch Principle 2. *(Built — plugins/calendar, db/migrations/0013_calendar.sql.)*
                                                                                                                                                           - **Frontend (`frontend/src/views/CalendarView.tsx`):** a new tab, same shape as `MealPlanView.tsx` — plain React + CSS, no FullCalendar/Shadcn, calling `get_calendar_schedule`/`create_calendar_event` through the existing `callTool` client. Read-only events show a source badge, matching §6.4/§6.5's precedent of surfacing sync status in-app rather than requiring a second app.
                                                                                                                                                           - **Tools (`plugins/calendar`):** `get_calendar_schedule(startDate, endDate, sources?)`, `create_calendar_event(title, start_time, end_time, description?, assigned_members?, linked_list_item_id?, linked_note_id?, visibility?)` (sets `source = 'native'`), `update_calendar_event(event_id, title?, start_time?, end_time?, description?, assigned_members?, visibility?)`, and `delete_calendar_event(event_id)` — the latter two were deferred "until real use shows they're needed"; bidirectional Google sync needing edit/delete parity in both directions is that use. Both operate on any event this user owns regardless of `source` (scoped by `event_id`/`user_id`, not source), so a Google-originated row is editable the same way a native one is; create/update best-effort push to Google afterward when the resolved `visibility` is `'shared'` and a connection is configured (`googleOutboundSync.ts`), never failing the tool call if that push fails — a `'private'` event skips the Google API entirely.

                                                                                                                                                           #### 6.8 Web Search *(built)*
                                                                                                                                                           A single `web_search(query, count?)` tool (`plugins/web`) backed by the Brave Search API, covering three use cases with one general-purpose tool rather than one each: recipe discovery (search finds a candidate URL, then hands off to the existing `import_recipe`, §6.5 — no new fetch/parse logic), code-pattern/documentation lookup (the LLM embeds operators like `site:github.com` directly in the query string), and general facts. Deliberately search-only, not a page-fetch tool: fetching an arbitrary LLM-chosen URL needs its own SSRF guard, since the orchestrator shares `traefik-net` with Postgres and other internal services. `import_recipe`'s equivalent fetch had exactly this gap and is now closed via `fetchUntrustedUrl` (`orchestrator/src/io/fetchUntrusted.ts` — DNS-resolves the hostname and rejects loopback/private/link-local/reserved addresses before fetching); any future page-fetch tool (`ingest_url`, §6.6) should route through the same wrapper rather than reopening this gap. Returns raw `{title, url, snippet}` per result; no summarization in the tool itself (Principle 2).

                                                                                                                                                           No RLS/user-scoping applies — results aren't household data. `BIGBRAIN_BRAVE_API_KEY` is a secret (Principle 12: an API key grants access on its own) resolved through `provider_credentials` (`brave_api_key`, `db/migrations/0016_web_search_credentials.sql`), same encrypted write-only shape as the LLM/Notion/calendar keys — rotated from the Settings tab, not a `.env` round-trip. Best-effort like Notion sync and calendar ICS feeds: no key resolved means `registerTools` returns no tools at all, so the LLM is never offered a tool that would just fail.

                                                                                                                                                           #### 6.9 Weather *(built)*
                                                                                                                                                           A `get_weather(location, units?, days?)` tool (`plugins/weather`) backed by Open-Meteo, chosen specifically because it needs no API key — unlike §6.8's Brave Search, there's no `provider_credentials` entry, no migration, and no Settings-tab wiring; `registerTools` registers the tool unconditionally. Two calls per invocation: Open-Meteo's free geocoding endpoint resolves whatever place name the LLM passes to lat/lon, then the forecast endpoint is called with those coordinates — there's no single-request "weather for this city" shape to collapse them into. An unresolved location returns `{found: false}` rather than throwing, same soft-not-found shape as `get_recipe`/meal planning (§6.5). The forecast's numeric WMO `weather_code` is mapped to a human description via a fixed lookup table (`weatherCodes.ts`, a Pure Function module — a published-standard mechanical mapping, not inference, so it doesn't touch Principle 2).

                                                                                                                                                           No RLS/user-scoping applies — weather isn't household data, same reasoning as §6.8.

                                                                                                                                                           #### 6.10 Scheduled Alarms & Agent Routines *(built — plugins/temporal, orchestrator/src/orchestrator/agentRoutineDispatch.ts, db/migrations/0031-0032/0035)*
                                                                                                                                                           The platform's way of moving through time without a user present: `scheduled_jobs` (`schedule_routine` tool) fires either a human-facing `'alarm'` (a bare reminder — `plugins/temporal/src/jobPoll.ts` flips its status/next_run_at, no reasoning involved) or an `'agent_routine'` — an unattended wake-up of the LLM reasoning loop itself, running inside its `linked_chat_id` (required at creation) so it inherits that chat's own tool allow-list/system prompt and leaves a real, readable transcript rather than acting invisibly. The wake-up is injected as a synthetic `'user'` message carrying the job's own `instructions`, clearly labeled as automatic. `'daily'` jobs recompute `next_run_at` via `nextOccurrence.ts`'s IANA-timezone-aware arithmetic (moved to `orchestrator/src/util/` once the dispatcher, living in core rather than a plugin, needed the same math `jobPoll.ts` already had — a plugin can depend on `@bigbrain/orchestrator`, never the reverse); a claimed job's state always advances *before* it actually runs, not after, so a crash mid-run skips one firing rather than risking a double-fire that bills the same routine's LLM usage twice.

                                                                                                                                                           **Addition — bb_principles.md §14: every LLM call passes through one gate, tagged with a task id (built — orchestrator/src/io/llm/llmGate.ts, db/migrations/0035).** `index.ts` gates the household's own `LlmProvider` exactly once, at boot; every downstream caller — `runTurn`'s own reasoning calls, any tool-triggered forced-schema call nested inside a turn (`classify_section`, `classify_note`, ...), a chat's per-profile connection override — shares that one instance without needing to change, since a gated `LlmProvider` has the identical `complete()` shape as a raw one. Which task a call belongs to travels via `callContext.ts`'s `AsyncLocalStorage` (the same pattern `io/logger.ts`'s `runWithRequestId` already established for request-scoped metadata), set once per turn by `runTurn` rather than threaded through every plugin helper's signature — a call made with no context set is a bug, not a degraded state, and the gate throws rather than logging an unattributed row. Every call is metered (`llm_calls`, an audit table deliberately RLS-exempt like `provider_credentials`/`orchestrator_settings`, since the household-wide cap genuinely needs to sum usage across every user); only `kind: 'agent_routine'` calls are ever refused or trip a breach reaction — a live conversation is never capped by an unattended routine's budget. Caps are two-tiered and rolling-24h: a **per-job** breach (`scheduled_jobs.max_runs_per_day`/`max_tokens_per_day`) flips that job's own `status` to `'capped'` (distinct from `'cancelled'` — the household can tell "the bot turned this off" from "a person did"); a **household-wide** breach (`orchestrator_settings.agent_routine_max_runs_per_day`/`max_tokens_per_day`) flips `agent_routines_enabled` itself — the literal same setting a Settings-tab manual kill switch controls, so an automatic trip and a human's own toggle are indistinguishable in code, not two parallel mechanisms to keep in sync. Token caps are necessarily a soft, after-the-fact ceiling (a call's own cost isn't known until it returns) — call-count caps are exact.

                                                                                                                                                           **Deferred — real token-level streaming, as insurance for a tighter mid-generation cutoff (designed, not built).** `server/httpServer.ts`'s `stream: true` today is not real streaming — `runTurn` resolves the full reply before anything is sent, then it's emitted as one shaped SSE chunk (that file's own doc). A genuine streaming `runTurn` would let a caller abort mid-generation on a token-count trigger, a strictly tighter enforcement than the pre-flight/post-hoc gate above. Not pursued now: it's a separate, sizable change to the core agentic loop's shape (not something that folds into the gate), and its protection is weakest exactly where `agent_routine` calls spend most of their time — mid-turn tool-calling rounds, where aborting a stream risks cutting a tool call's arguments off mid-JSON, not the final user-facing reply. Worth building if a single runaway call ever actually proves to be the failure mode in practice, rather than the aggregate daily caps above.
